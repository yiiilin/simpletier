# Security Protocol Research (Not an Approved Contract)

> Research only. This note does not approve a message cap, NetworkID width, KDF change, or Noise parameter. Official primary sources were fetched and checked directly; the NIST source caveat is noted below.

## Concrete ChaChaPoly and released Noise follow-up (full-function goal round 1)

Provenance: independent read-only research subagent `9e682540-49b7-46b5-b86f-28a3817bc141` fetched the primary sources below. It did not modify dependencies, execute Noise tests or certify interoperability. These findings remove factual unknowns; they do not select a project risk target or approve a protocol change.

- [RFC 9001 §6.6](https://www.rfc-editor.org/rfc/rfc9001.html#section-6.6) says the ChaChaPoly confidentiality limit exceeds QUIC's possible `2^62` packet numbers. Its `2^36` integrity quantity counts failed authentications across all keys over a connection, not successful encryptions per key. Appendix B derives AES-GCM/CCM, not ChaChaPoly; its size/advantage constants cannot be repurposed as a proof for SimpleTier.
- [RFC 8446 §5.5](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.5) says ChaChaPoly sequence counters wrap before its safety limit; `2^24.5` TLS records and the cited approximately `2^-57` margin are AES-GCM guidance. TLS plaintext/nonce assumptions are not the custom 64 KiB SimpleTier context. Neither RFC supplies a universal 24-hour key-age rule.
- Official [CFRG AEAD-limits draft revision 13 §6.3](https://www.ietf.org/archive/id/draft-irtf-cfrg-aead-limits-13.txt) gives ideal-PRF single-key integrity `IA <= v*(L'+1)/2^103`, where v counts failed verifications and L' counts AAD/plaintext Poly1305 blocks. It is a draft, not a final RFC. The single-key confidentiality statement excludes underlying ChaCha PRF advantage; it is not unconditional unlimited use. The stronger §7.2 multi-key result assumes secret nonce randomization, which public Generation32|Counter64 does not supply. See the directly checked [multi-user proof](https://eprint.iacr.org/2023/085.pdf), Theorems 6.1/7.2 and §7.4. Conservative per-key union accounting must include actual padded AAD/ciphertext/length blocks and primitive advantages. The older [RFC 8439 §4](https://www.rfc-editor.org/rfc/rfc8439.html#section-4) term n/2^102 remains a conservative failed-forgery term, not a successful-call cap.
- Example only: if the real construction establishes L'+1 <= 2^13 and the owner chooses p=2^-57, the single-key draft expression allows v<=2^33 failed verifications; v<=2^32 leaves extra margin. This is NOT an approved quota, not a successful-encryption limit, and not automatically deployment-wide risk. Extra/duplicated AAD must be counted; <=65536 on-wire bytes alone is insufficient.
- Verified [flynn/noise v1.1.0](https://github.com/flynn/noise/tree/v1.1.0) is the latest tagged module observed by the research. Suite APIs and [state.go](https://github.com/flynn/noise/blob/v1.1.0/state.go) support HandshakeXX + PSK placement3 and HandshakeIK + placement2, DH25519/CipherChaChaPoly/HashSHA256. The exact [vectors](https://github.com/flynn/noise/blob/v1.1.0/vectors.txt) contain four cases of each requested pattern; [vector_test.go](https://github.com/flynn/noise/blob/v1.1.0/vector_test.go) consumes them. The [generator](https://github.com/flynn/noise/blob/v1.1.0/vectorgen/vectorgen.go) uses the same library: genuine library regression support, not independent SimpleTier interoperability.
- Split outputs are canonical initiator->responder then responder->initiator on BOTH peers; responders must reverse TX/RX selection. UnsafeKey exports a copied Split transport key, not chainingKey or a standard exporter. Cipher() uses Noise's uint64 nonce encoding, incompatible with arbitrary repo GenerationBE32|CounterBE64. A reviewed application adapter would export once after completion, derive domain/context-separated app keys, and never also use the original Split states for transport. XXpsk3 initiator finishing Msg3 does not by itself confirm responder PSK possession/receipt; bidirectional encrypted CAPABILITY remains required. Similarly IK local final write cannot substitute for the E2E READY/key-confirmation gate.

Minimal proposed freeze, still requiring acceptance of affected behavior: bind an unambiguous length-prefixed full raw name/canonical CIDR descriptor into PSK expansion, Link/Session prologues and child-key context; use full ContextID for memory/persistent partitions while u64 NetworkID remains a locator. Make first Session attempt=0,target_epoch=1 with an explicit haveAttempt flag, cached byte-identical per-step retransmissions and terminal restart using fresh SessionID. Monitor each directional key domain separately; rekey requests from either direction are authenticated, only Path owner starts Session IK, and hard limits fail closed. Session rekey does not renew Link control/bootstrap keys. Operational successful-call/byte/key-age limits and whether Link expiry resets existing long streams versus adding in-place Link rekey are availability/security decisions, not library facts.

## ChaCha20-Poly1305 usage limits

RFC 8439 separates a **per-invocation data limit** from **nonce uniqueness across invocations**. In the IETF ChaCha20 variant, the block counter is 32 bits and blocks are 64 bytes; the AEAD construction sets `P_MAX` to `(2^32 - 1) * 64 = 274,877,906,880` plaintext bytes for one invocation. RFC 8439 also requires a distinct 96-bit nonce for every invocation under a fixed key. Thus, `2^32 - 1` is a block/data bound for one AEAD call, not a cap of `2^32` messages per key. ([RFC 8439 §2.3](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.3); [RFC 8439 §2.8](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8); [RFC 5116 §3.1](https://www.rfc-editor.org/rfc/rfc5116.html#section-3.1); [RFC 5116 §4](https://www.rfc-editor.org/rfc/rfc5116.html#section-4))

RFC 5116 requires each AEAD algorithm to specify algorithm-specific `P_MAX`, `A_MAX`, nonce-length bounds, and `C_MAX`; its interface does not define a universal per-key invocation-count field. It does require nonce values to be distinct for each invocation with the same key, and describes persistent nonce state when a key survives reboots. RFC 8439 §4 explains that nonce reuse repeats both the one-time Poly1305 key and keystream, exposing the XOR of plaintexts and undermining authenticity. ([RFC 5116 §3.1](https://www.rfc-editor.org/rfc/rfc5116.html#section-3.1); [RFC 5116 §4](https://www.rfc-editor.org/rfc/rfc5116.html#section-4); [RFC 8439 §4](https://www.rfc-editor.org/rfc/rfc8439.html#section-4))

RFC 8439 §4 gives a Poly1305 forgery-rejection bound parameterized by message length and discusses it even after `2^64` legitimate messages. That is an analysis statement, not a recommended operational cap. A generic `2^32-message` limit is not established by RFC 8439; any application cap must account for the selected AEAD, bytes/blocks per invocation, nonce uniqueness and exhaustion, key lifetime, direction/key partitioning, restart persistence, and the accepted forgery-risk target. ([RFC 8439 §4](https://www.rfc-editor.org/rfc/rfc8439.html#section-4); [RFC 5116 §3.1](https://www.rfc-editor.org/rfc/rfc5116.html#section-3.1))

## Noise CipherState and rekeying

Noise Protocol Framework revision 34 models each transport direction with its own `CipherState`; the final handshake returns two states, initiator-to-responder and responder-to-initiator. A `CipherState` carries a 32-byte key and 64-bit nonce counter; the maximum nonce value is reserved and nonce exhaustion is an error. For `ChaChaPoly`, Noise encodes its 64-bit counter into the low 64 bits of the 96-bit AEAD nonce, with 32 high zero bits. ([Noise §5.1](https://noiseprotocol.org/noise.html#the-cipherstate-object); [Noise §5.2](https://noiseprotocol.org/noise.html#the-symmetricstate-object); [Noise §5.3](https://noiseprotocol.org/noise.html#the-handshakestate-object); [Noise §12.3](https://noiseprotocol.org/noise.html#the-chachapoly-cipher-functions))

Noise leaves rekey timing to the application: examples include per-message, after a chosen message count, or another signaled criterion. `Rekey()` changes the CipherState key but does not reset its nonce counter; the framework requires a new handshake before a CipherState sends `2^64` or more transport messages. The Noise security section's explicit `2^56`-byte-per-key data-volume caution is for `AESGCM`, not `ChaChaPoly`; it should not be transferred as a ChaCha20-Poly1305 cap. ([Noise §11.3](https://noiseprotocol.org/noise.html#rekey); [Noise §14](https://noiseprotocol.org/noise.html#security-considerations))

Consequently, a cap on messages **per key** is application policy: it depends on when rekey replaces the key, how much data each invocation processes, the AEAD's own per-call bound, and the nonce state retained by each directional CipherState. Rekeying may lower bytes per key, but in Noise it does not reset the 64-bit counter; direction-specific counters/keys must not be accidentally shared. No universal `2^32` message cap follows from these sources. ([Noise §5.1](https://noiseprotocol.org/noise.html#the-cipherstate-object); [Noise §5.2](https://noiseprotocol.org/noise.html#the-symmetricstate-object); [Noise §5.3](https://noiseprotocol.org/noise.html#the-handshakestate-object); [Noise §11.3](https://noiseprotocol.org/noise.html#rekey); [RFC 8439 §2.3](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.3); [RFC 8439 §2.8](https://www.rfc-editor.org/rfc/rfc8439.html#section-2.8))

## 64-bit NetworkID as a domain identifier

The current repository specification computes `NetworkID = SHA-256("simpletier-v1" || 0x00 || name_utf8_raw || 0x00 || canonical_cidr_utf8)[0:8]`; the wire envelope carries it as `u64be`. The PSK formula uses raw `network.name` as HKDF salt, the token as input keying material, and a constant info string; the CIDR is not directly in that PSK formula. The Noise prologues include NetworkID, not the full canonical CIDR. ([Topology/Routing :399](../internals/topology.md#L399); [Security :20, :44](../internals/security.md#L20); [Wire :233](../internals/wire.md#L233))

For an ideal hash truncated to `λ` bits, NIST SP 800-107 Rev. 1 states that expected collision resistance falls to `λ/2`; a 64-bit truncation therefore gives about 32 bits of generic collision work, not 64 bits. Whether accidental collisions are tolerable depends on the number of distinct network descriptors; if an adversary can choose descriptors and search offline, the generic collision work factor is also about `2^32`. This is not enough to describe the ID as a 128-bit collision-resistant security boundary. ([NIST SP 800-107 Rev. 1 §§4.1, 5.1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-107r1.pdf); [NIST publication status note](https://csrc.nist.gov/pubs/sp/800/107/r1/final))

Noise prologue bytes are hashed into the handshake hash; different prologues make the handshake fail, but Noise explicitly says prologue data is not mixed into encryption keys. By contrast, RFC 5869 identifies HKDF's `info` input as the place to bind derived key material to application/context-specific information and to prevent equal derived keys across contexts when the same IKM is used. Under the current formula, different names affect the PSK salt, but two configurations with the same name/token and different CIDRs derive the same PSK; CIDR is represented only through the truncated NetworkID in the prologue/envelope. ([Noise §6](https://noiseprotocol.org/noise.html#prologue); [RFC 5869 §3.2](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.2); [Security :20, :44](../internals/security.md#L20))

## Choices and implications (none selected here)

- **Widen NetworkID:** raises generic collision work according to output width (`λ/2` bits under the cited truncation model). The current envelope specifies `NetworkID:u64be`, so changing its width affects wire layout and compatibility; widening the identifier alone still does not mix it into Noise-derived keys. ([NIST SP 800-107 Rev. 1 §5.1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-107r1.pdf); [Wire :233](../internals/wire.md#L233); [Noise §6](https://noiseprotocol.org/noise.html#prologue))
- **Bind canonical context into key derivation and/or the prologue:** including canonical CIDR (and the intended network name) in HKDF `info` would derive context-specific PSKs; including it in the Noise prologue would make peers confirm the same full context, but prologue-only binding is transcript confirmation, not key derivation. Either changes the current handshake/key schedule and needs its own protocol revision and interoperability review. ([RFC 5869 §3.2](https://www.rfc-editor.org/rfc/rfc5869.html#section-3.2); [Noise §6](https://noiseprotocol.org/noise.html#prologue); [Security :20, :44](../internals/security.md#L20))
- **Keep 64 bits and accept/document risk:** preserves the current field but accepts the associated namespace-collision risk. The acceptable population, adversary capability, and operational response to a collision are product/security decisions; this note does not choose them. ([Topology/Routing :399](../internals/topology.md#L399); [NIST SP 800-107 Rev. 1 §5.1](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-107r1.pdf))

**NIST caveat:** NIST's publication page carries a 2022-12-20 planning note that NIST decided to withdraw SP 800-107 Rev. 1. It is cited above only for its explicit hash-truncation strength analysis, not as current protocol approval or a current normative requirement. ([NIST publication page](https://csrc.nist.gov/pubs/sp/800/107/r1/final))
