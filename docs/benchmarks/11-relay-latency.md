# 中继延迟与吞吐基准

测量时间：2026-10-23
环境：本机回环，8 核，Linux；延迟由 `tc netem` 在内核注入

## 测量方法

`tests/roomscale -transfer`：100 个房间，每房间 10 个成员，共 1000 个 peer。
每房间挑 1 对成员传输 50 MB，双向各一次。

其中一侧的 carrier 走**延迟入口端口**，该端口的流量由 `tc netem` 施加单程 150 ms
± 50 ms 抖动。另一侧走普通端口，不受影响。

**为什么用 netem 而不是用户态代理**：用户态代理必须先定义「一个 chunk 是什么」，
而任何定义在某些场景都是错的。按 read 调用计延迟时，一次 3 往返的 Noise 握手会
因为拆成十个小分段而付出十次延迟，实测把 3 次往返放大成 8 次。内核在网络包层延迟，
与真实慢链路一致。

## 结果

| 指标 | 上传 | 下载 |
|---|---|---|
| 均值 | 5.31 MB/s | 6.17 MB/s |
| p50 | 5.06 | 6.40 |
| p90 | 6.90 | 7.75 |
| min | 3.29 | 3.27 |
| max | 9.16 | 9.70 |
| **聚合** | **525.99 MB/s** | **610.79 MB/s** |

| 指标 | 数值 |
|---|---|
| 加入 | 1000/1000，7.9 s（136 peers/s）|
| 传输完成 | 99/100 房间，75.5 s |
| 往返延迟 p50 | 345 ms |
| 往返延迟 p90 | 968 ms |
| 往返延迟 p99 | 1.675 s |

标称往返延迟为 300 ms（2 × 150 ms），p50 与之一致。

## 已知问题

**尾部延迟显著高于标称值**：p90 是标称的 3.2 倍，p99 是 5.6 倍。

这发生在 100 对并发传输时，属排队现象而非链路问题。可疑点包括 netem 队列长度上限
（默认 `limit 1000` 个包）、1000 个 peer 共享单进程 CPU，以及 relay 转发路径上的
逐帧处理。

**尚未定位到具体原因**，不将任何一条当作结论。

## 测量限制

- 所有 peer、relay 与延迟注入共享同一台机器和同一个进程，CPU 是共同瓶颈
- 回环没有真实网络的丢包与乱序
- 延迟由内核注入到指定端口，因此测的是 relay 转发路径对高延迟的响应，不是真实
  广域网的端到端表现

# 多进程并发基准（2026-10-23 补测）

上一节的测量把所有 peer、relay 与延迟注入放在**同一个进程**里。那样测出来的每对速率
被 Go 调度器争抢拉低：单对在两个独立进程中是 40 MB/s，在同一进程内只有 11 MB/s。

本节改成每个节点一个独立 OS 进程，经真实回环 socket 与 relay 通信。

## 工具

- `examples/nodeproc`：一个进程 = 一个 relay 或一个 peer。peer 可监听虚拟端口做 echo，
  或向另一个 peer 的虚拟地址推送固定时长，然后打印自己的结果。
- `tests/roomscale/multiproc.sh`：启动 relay、每对一个 echo 进程、每对一个推送进程，
  汇总每对与聚合速率。每个房间使用独立 token——共用一个 token 会让所有房间落进同一个
  虚拟网段，表现为 `route conflict` 而不是预期的多房间隔离。

## 结果

20 房间 × 10 进程 = 200 个独立进程，100 对并发，20 秒窗口：

| 指标 | 上传 | 下载 |
|---|---|---|
| 均值 | 1.59 MB/s | 1.30 MB/s |
| p10 | 1.05 | 0.66 |
| p50 | 1.37 | 1.07 |
| p90 | 2.63 | 2.27 |
| min | 0.42 | 0.00 |
| max | 3.58 | 3.24 |
| 聚合 | 152.46 MB/s | 124.38 MB/s |

成功率 100/100。

对照组（同一台机器、同一程序）：

| 规模 | 聚合上传 | 每对 p50 |
|---|---|---|
| 4 对 | 135 MB/s | 40.26 MB/s |
| 20 对 | 136 MB/s | 6.59 MB/s |
| 100 对 | 152 MB/s | 1.37 MB/s |

## 结论与限制

**聚合吞吐在 135–152 MB/s 之间饱和**，与并发对数无关。测量时负载均值达到 24（8 核），
即 3 倍超订。因此：

- 聚合上限来自这台机器的 CPU（加密是主要成本），不是 overlay 的并发设计
- 每对之间的差（p10 与 p90 相差 2.5 倍）来自操作系统在超订下的调度，不是分配不均
- **未测出产品层面的并发缺陷**；100 对并发下 100/100 成功，无会话丢失

要得到不受 CPU 限制的每对速率与更窄的分布，需要多机部署，或把进程数降到 CPU 不超订的
规模（约 40–50 个进程）。本报告不声称在单机 200 进程下达到稳定速率。
